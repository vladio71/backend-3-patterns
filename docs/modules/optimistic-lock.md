# Оптимістичне блокування: version у PATCH

Код: `src/modules/products/products.service.ts` (`update`), `product.entity.ts` (`@VersionColumn`).

## Проблема

Два менеджери відкрили картку одного товару. Перший змінив ціну і зберіг. Другий, який досі бачить стару ціну, змінив назву і зберіг. Його форма відправила всі поля, включно зі старою ціною. Зміна першого зникла, і ніхто не отримав помилки.

## Наївне рішення і де воно ламається

```ts
const product = await repo.findOne(id);
product.name = dto.name;
product.priceCents = dto.priceCents;
await repo.save(product);
```

Сценарій:

```
час   менеджер А                       менеджер Б
1     GET  -> {price: 100, name: 'X'}
2                                      GET  -> {price: 100, name: 'X'}
3     PATCH {price: 200}  -> save
4                                      PATCH {name: 'Y', price: 100} -> save
5     у базі: {price: 100, name: 'Y'}  зміна А втрачена
```

Це "lost update". Жодна помилка не виникає, тому його помічають через тиждень.

## Правильне рішення

Клієнт разом зі змінами надсилає `version`, яку бачив. Сервер оновлює рядок лише якщо версія в базі досі та сама:

```sql
UPDATE products
   SET name = $1, version = version + 1, updated_at = now()
 WHERE id = $2 AND tenant_id = $3 AND version = $4 AND deleted_at IS NULL
```

`affected = 1`: зміна прийнята, версія стала `version + 1`.
`affected = 0`: хтось уже змінив рядок. Сервер перечитує поточну версію і відповідає `409 { code: 'STALE_VERSION', currentVersion: 2 }`. Фронтенд показує "товар змінено, перечитайте" і робить GET.

Один `UPDATE` з умовою атомарний: між перевіркою версії і записом немає вікна, Postgres робить це на одному рядку за одну операцію.

Важливо: `@VersionColumn` у TypeORM сам тільки збільшує `version` при `save()`. Він НЕ додає `WHERE version = ...`, тому `save()` не захищає від lost update. Умову пишемо явно, тому в `update` використано QueryBuilder.

### Порівняння з песимістичним FOR UPDATE

У саґі (`checkout.service.ts`, `reserveStock`) використано інший підхід: `SELECT ... FOR UPDATE`, тобто песимістичне блокування.

```
                      оптимістичне (version)            песимістичне (FOR UPDATE)
хто чекає             ніхто, другий отримує 409        другий чекає на COMMIT першого
коли конфлікт         рідко (люди редагують картки)    часто (кожен checkout б'є в stock)
між читанням і        може бути хвилина (форма у       мілісекунди (одна транзакція)
записом               браузері)
де тримається стан    у клієнта (version)              у базі (lock на рядку)
що робити при         перечитати і повторити вручну    нічого, просто чекати
конфлікті
```

Правило: якщо між "прочитав" і "записав" стоїть людина або HTTP-запит до іншого сервісу, тільки оптимістичне. Якщо все в одній транзакції і конфлікти часті, `FOR UPDATE`.

## Тест, який це доводить

`test/e2e/optimistic-lock.e2e-spec.ts`:

- "другий PATCH зі старою version": перший PATCH з `version: 1` повертає `version: 2`; другий з `version: 1` отримує 409 `STALE_VERSION` і `currentVersion: 2`; назва в базі від першого; повтор з `version: 2` проходить.
- "паралельні PATCH з однією version": 5 одночасних запитів, рівно один 200, чотири 409.
- "PATCH без version": 400 від валідації.
