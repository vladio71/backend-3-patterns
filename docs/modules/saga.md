# Саґа: оформлення з трьох кроків і компенсації

Код: `src/modules/checkout/` (сервіс, resumer, таблиця `checkout_sagas`).

## Проблема

`POST /checkout` робить три речі: резервує товар на складі, списує гроші, створює відправлення. Кожна з них окрема: склад і відправлення у нашій базі, платіж у зовнішнього провайдера. Якщо гроші списати не вдалося, резерв треба повернути. Якщо відправлення не створилось після успішного списання, гроші треба повернути.

## Наївне рішення і де воно ламається

```ts
await reserveStock(items);
await payments.charge(amount);     // кинув помилку
await createShipment(order);
```

Сценарій: платіж відхилено (`X-Fail-Payment: 1` або сума на .99). Функція кидає виняток, клієнт бачить 402. Але `reserveStock` уже виконався: `products.stock` зменшено, а замовлення нікому не належить. Через годину товару "немає", хоча він на полиці.

Обгорнути все в одну транзакцію Postgres не вийде: `payments.charge` це HTTP-запит до іншої компанії, його не відкотити командою `ROLLBACK`.

Другий сценарій: процес API упав після `charge`, але до `createShipment`. Гроші списані, відправлення немає, ніхто не знає, що саме треба доробити.

## Правильне рішення

Саґа: послідовність кроків, де кожен крок має компенсацію, і стан прогресу живе в базі (`checkout_sagas`: `step`, `status`, `compensations_done`, `payload`).

```
крок            компенсація
reserve_stock   release_stock
charge_payment  refund
create_shipment (немає: це останній крок)
```

`CheckoutService.run(saga)` виконує кроки з `saga.step`. Кожен крок сам записує в базу і свій ефект, і перехід на наступний крок. При помилці:

```
status = compensating
  є paymentRef і немає 'refund' у compensations_done   -> refund, записати 'refund'
  step пішов далі за reserve_stock і немає 'release_stock' -> повернути stock, записати 'release_stock'
  order.status = cancelled, подія outbox order.cancelled
status = compensated
```

Кожна компенсація записується в `compensations_done` одразу після виконання. Тому `compensate` можна викликати двічі, і refund не повториться.

### Чому компенсації у зворотному порядку

Пізніший крок спирається на результат раннього, тому скасовувати його треба раніше. Приклад: платіж пройшов, а відправлення не створилось, і треба повернути гроші та склад. Якщо спершу повернути товар на полицю (`release_stock`), а потім `refund` впаде (провайдер лежить), то товар уже міг купити хтось інший, а перший клієнт лишається списаним за скасоване замовлення. У зворотному порядку першим іде `refund`: якщо він упав, резерв на складі ще тримається, саґа лишається `compensating`, і resumer повторить усе, коли провайдер оживе. Склад повертається лише після того, як гроші вже повернуто.

### Чому крок і перехід в одній транзакції

Крок `reserve_stock` зменшує `products.stock` і переводить саґу на `charge_payment`. Це один `COMMIT`:

```
BEGIN
  SELECT ... FROM products ... FOR UPDATE
  UPDATE products SET stock = stock - $qty
  UPDATE checkout_sagas SET step = 'charge_payment', payload = ...
COMMIT
```

Якби це були дві окремі транзакції, між ними лишалося б вікно для падіння процесу. Склад списано, а `saga.step` ще `reserve_stock`. Що тоді зробить resumer, залежить від статусу:

```
status = running      -> виконає reserve_stock вдруге: склад списано двічі
status = compensating -> побачить step = reserve_stock, вирішить, що резерву не було,
                         і НЕ поверне товар: він зник зі складу назавжди
```

В одній транзакції стану "ефект є, а step не змінився" не існує: або є обидва, або жодного. Те саме для `create_shipment`: відправлення і перехід на `done` (разом зі `status = completed`) фіксуються разом. Створення замовлення і рядка саґи в `checkout` теж одна транзакція, інакше падіння між ними лишило б `pending`-замовлення без саґи, яке ніхто не доведе до кінця.

Крок `charge_payment` має вікно, яке транзакцією не закрити: провайдер уже списав гроші, а наш `COMMIT` ще не відбувся. Тому виклик провайдера ідемпотентний, ключ це `orderId` (`FakePaymentProvider` пам'ятає `orderId -> paymentRef` і на повторний виклик віддає ту саму оплату; справжні провайдери роблять це через заголовок `Idempotency-Key`). Перед викликом провайдера крок ще дивиться в таблицю `payments`: якщо платіж для замовлення вже записано (наприклад, прийшов вебхук), провайдера не чіпаємо взагалі. Resumer після падіння знову виконає `charge_payment`, отримає ту саму оплату, і клієнта списано один раз.

Резерв складу робиться під блокуванням рядка (`SELECT ... FOR UPDATE` у `reserveStock`): два паралельних checkout на останню одиницю товару стають у чергу, другий бачить `stock = 0` і падає на першому кроці.

Падіння процесу: саґа лишається зі `status = running`. `SagaResumer` (worker) раз на `SAGA_RESUME_POLL_MS` (5 секунд) бере саґи, які не оновлювались довше за `SAGA_RESUME_AFTER_MS`, найстаріші першими (`ORDER BY updated_at`), і викликає той самий `run(saga)`. Виконані кроки не повторюються, бо `saga.step` уже вказує на наступний.

Перед запуском resumer саму саґу "захоплює":

```sql
UPDATE checkout_sagas SET updated_at = now()
 WHERE id = $1 AND status = $2 AND updated_at < $stale
```

Якщо `affected = 0`, саґу вже взяв інший resumer (або вона ожила сама), і поточний її пропускає. Без цього два екземпляри worker-а отримали б з бази один і той самий список і обидва виконали б одну саґу: два `charge`, два відправлення.

### Звідки береться SAGA_RESUME_AFTER_MS

Саґа вважається покинутою, якщо `updated_at` старіший за `SAGA_RESUME_AFTER_MS` (типово 30 с). Це число має бути набагато більшим за найдовший крок. Найдовший крок це виклик провайдера, і він обмежений `BREAKER_CALL_TIMEOUT_MS` (2 с) плюс кілька запитів у базу. 30 с це ~15 таймаутів: живий HTTP-запит, який просто чекає відповіді провайдера, не схожий на мертвий. Якщо поставити значення менше за таймаут, resumer почне виконувати крок паралельно з HTTP-запитом, який ще працює (claim від цього не рятує: `updated_at` ще старий). Верхня межа інша: що більше значення, то довше клієнт чекає на доведення саґи після падіння (`SAGA_RESUME_AFTER_MS` плюс до `SAGA_RESUME_POLL_MS`). У тестах стоїть `0`, щоб `tick()` одразу підхоплював саґу.

Заголовок `X-Crash-After: reserve_stock` імітує падіння після кроку: саґа лишається `running`, HTTP отримує 500 `SIMULATED_CRASH`.

## Тест, який це доводить

`test/e2e/saga.e2e-spec.ts`:

- "платіж відхилено": 402 `CHECKOUT_FAILED`, `step = charge_payment`; `products.stock` знову 5; `checkout_sagas.status = compensated`, `compensations_done = ['release_stock']`; замовлення `cancelled`; у `shipments` нічого.
- "недостатньо товару": падіння на `reserve_stock`, компенсацій немає, платежу немає.
- "падіння процесу після reserve_stock": після 500 саґа `running` зі `step = charge_payment`; `SagaResumer.tick()` доводить її до `completed`, stock списано один раз.
- "атомарність кроку і переходу": тригер у тестовій базі ламає запис `saga.step`; склад, платіж або відправлення відкочуються разом із ним (без однієї транзакції stock лишався б списаним).
- "charge_payment ідемпотентний": провайдер списав, а база нічого не знає; resumer отримує ту саму оплату, а не другу. Якщо платіж уже записано вебхуком, провайдера не викликають.
- "два resumer-и паралельно": `run` для однієї зависшої саґи викликається один раз.
- "запис саґи впав": замовлення і подія `order.created` теж не створені.

## Спробуй сам

1. Додай четвертий крок `send_receipt` (подія в outbox) з компенсацією `cancel_receipt`. Перевір, що при падінні на ньому refund і release_stock виконуються в правильному порядку.
2. Resumer захоплює саґу через `updated_at`, але живий API-процес, який виконує довгий крок, `updated_at` не оновлює. Зроби так, щоб виконавець "продовжував оренду": під час довгого кроку раз на кілька секунд оновлювати `updated_at`. Тоді `SAGA_RESUME_AFTER_MS` можна зменшити нижче таймауту провайдера.
